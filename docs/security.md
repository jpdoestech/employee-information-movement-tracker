# Security model and review notes

Organization grants and field policies are separate normalized records. C creates a value, R reads it, U replaces it, and D clears it; U does not imply R or D. Viewer cannot mutate employee data even if an erroneous grant says otherwise. Role defaults can be represented by role policies; shipped ordinary roles have no blanket data grants. Superadmin is an explicitly trusted configuration/data override within active field applicability. Permission administration and correction remain Superadmin-only; there is no unconstrained delegated permission-admin role.

Every ordinary read/write validates the live active profile, effective primary placement and organization action. A field must be active in an active group and applicable. Direct deny wins over direct allow; direct allow can override group deny; restricted fields require a direct field allow; group deny wins over inherited group allow; otherwise deny. Matching user/role policies at a level follow the same deny precedence. Group inheritance is evaluated dynamically and requires `inherit_new`; creating a field never copies or manufactures grants. Head Office/unassigned are explicit, and branch client inclusion is opt-in. The Permissions preview reports the decision and matching policy reference for each action.

All application tables enable RLS and deny ordinary base-table privileges. Public secured RPCs are the only browser data API. Private helpers use a fixed empty search path and cannot be invoked by API users. Raw employee Realtime is not configured. JSONB key projection precedes search, filters, sorting, aggregate counts and export. No localStorage employee cache exists; personal layout IDs and synthetic preview layouts are the only persistent app preferences. Auth's normal session handling remains in the Supabase SDK. Authorized catalogs refresh on focus and every 30 seconds; writes and reads enforce revocations immediately regardless of that UI interval.

Statement-scoped read matrices evaluate the same field evaluator once per distinct placement; they never persist across requests/principals. Metadata catalogs reveal only actionable fields, except the explicitly authorized schema configuration screen. Blind U forms expose a new-value input without the old value. Denied keys are rejected atomically rather than dropped. Hidden stored values survive patches, field scope changes and transfers. Required applicable destination values must be supplied with authorization; otherwise the transaction rejects with an escalation message. Future destination values are stored on the shared profile immediately, while placement visibility changes on the effective date; plan entry accordingly. Voiding movement does not undo explicitly entered profile values—correct these separately with authorized versioned edits.

Mutations serialize on the state row and lock employee records, validate expected revisions, and commit audit/outbox together. This intentionally simple strategy favors correctness; measure contention before expanding throughput. Primary `[start,end)` ranges have a database exclusion constraint. Corrections void retained events and restore assignment intervals; they do not delete history. Idempotency is actor/request/payload-bound; frontend retries preserve request IDs in memory. Duplicate field labels are globally unique after NFKC/full Unicode case-fold and collapsed whitespace; punctuation is preserved. UUIDs and machine keys are immutable, including archived fields. Group names use the same organization-wide namespace.

Audit records contain actor, timestamp, reason and previous/next policy references, not employee value payloads. Ordinary delegated audit readers are limited to current accessible employee references and cannot see field keys/reasons. Movement history checks original and destination scopes and redacts values/reasons. Service credentials and encrypted OAuth tokens are private backend state. The worker service role can access export snapshots by design; treat its secret and deployment control as privileged.

Local tests exercise actual database roles/constraints and malicious RPCs. Separate real Supabase users/REST, PostgreSQL 17 compatibility, hosted security settings, Google failure behavior and deployed headers remain release gates. See [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [function security](https://supabase.com/docs/guides/database/functions). Never infer production security from the synthetic UI preview.
